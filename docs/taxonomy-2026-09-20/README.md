## 建議先採四個入口，保留專題深度

推薦試行「閱讀與觀看、身體與自己、助人工作、生活與實作」。最重要的改變是：每篇只選一個主要歸屬，主題可以跨類，連載不用再成為一個主分類。既有文章網址原則上全部保留。

目前的雜亂感有實際原因：網站只有五個 category，卻有 41 個已發布文章使用的 tag、16 種文章目錄；會所又在畫面上被當成第六類。讀者眼前同時出現主題、媒介、系列、方法學，作者則還得思考文章究竟要存進哪個目錄。這不只是標籤太多，而是不同用途的名字被放在同一層。

9 月 12 日報告主張保留五類；本次重新納入筆記庫與未來單次文章後，我更傾向合併「病痛經驗／成為自己」的頂層入口，並把「日常書寫」改成能明確接納工具、開箱、實作的入口。這是編輯判斷，不是由篇數自動推導的唯一答案。

## 我看見的書寫主線

你的文章常從一個微小現場開始：手如何畫線、會員如何握東西、一段話為什麼讓人有感、身體如何疼痛。接著，你會拿閱讀或工作經驗與它對照，最後重新理解自己與別人的處境。「聆聽、理解、表達、關係與存在感」是跨越許多文章的線索。

這條線索可以作為網站的作者介紹與專題導讀，但不宜變成每篇都必填的分類條件。你也會記錄工具、訓練、旅程、遊戲與生活小事，網站應容許它們單純存在。

| 閱讀證據 | 對分類的啟發 |
| --- | --- |
| 〈素描01：盲畫〉從畫線談到感官、自信、正念與自我對話 | 素描是一種實作與連載，也能跨連正念；不用在「藝術」與「心理」間強迫二選一 |
| 〈標本：凝視與被凝視〉把自身病痛、實習、自我揭露與身份放在一起 | 身體與自我理解長期交錯，合併入口有實質依據；若保留五類也必須寫清楚判準 |
| 〈行動科學到開放式對話：人們用行動在對話〉以閱讀去理解工作方法 | 讀過書不代表一定放閱讀；主旨在實務時可放助人工作，書名與方法作串連 |
| 《綠洲》心得從電影走向失語、主體與對話 | 保留作品心得入口很有價值，不必因談心理／障礙而把電影心得全部拆散 |
| 〈網頁架設學習歷程〉已經記錄 Obsidian、部署與工具學習 | 工具內容並非全新的異物，「生活與實作」有既有文章可作起點 |
| 筆記庫的游泳、重訓與素描樣本 | 同時有純技術紀錄、身體覺察與心情書寫；不能單靠「運動」關鍵字自動歸類 |
| 旅行、零碎心情與待分類樣本 | 行程、觀察、靈感、短詩是不同完成階段與形式，不宜把私人資料夾直接複製成公開分類 |

## 四類方案的使用規則

| 主分類 | 讀者來這裡找什麼 | 納入 | 邊界 |
| --- | --- | --- | --- |
| 閱讀與觀看 | 你如何理解一部作品或一份材料 | 書評、書摘、影劇心得、以整理材料為主的講座筆記 | 素材只是引子、重心在自己的實際工作或經驗時，依重心歸類 |
| 身體與自己 | 你如何感受身體、理解自己、與人相處 | 病痛敘事、身體覺察、情緒、親密關係、個體化、個人正念經驗 | 工作中的介入方法屬助人工作；純訓練操作屬生活與實作 |
| 助人工作 | 如何理解與支持人，以及工作中的困惑 | 會所、社工反思、對話方法、社會議題與助人實務、相關研究反思 | 以自身病痛為中心的文章不因發生在督導場合就自動算工作文 |
| 生活與實作 | 你做過、用過、去過與創作過什麼 | 工具教學、網站學習、店家／物品開箱、旅行、素描、生活觀察與創作 | 這是有正面定義的實踐入口，不是所有難分類文章的垃圾桶 |

名稱仍可討論：如果「身體與自己」太抽象，可以考慮「身體與生活」，但這會更容易和生活與實作重疊；目前較偏好前者。「閱讀與觀看」涵蓋電影更自然，但若你特別喜歡「閱讀與筆記」的語感，也可以保留原名。

**五類備案**：若你希望讀者一眼就看見病痛書寫，保留「病痛經驗、成為自己」兩類，其他三類採上表範圍。這比硬湊四類更合適。四類方案的代價是病痛在頂層不再獨立，因此必須同時保留清楚的「聆聽疼痛」專題入口。三類方案則會把大量內容塞進個人生活，本次不推薦。

### 新文章的 30 秒決策

1. 想一句話：這篇主要想分享什麼？
2. 主要是理解作品 → 閱讀與觀看；理解／支持人的工作 → 助人工作；自己的身體、情緒、關係 → 身體與自己；做法、體驗、行程、創作 → 生活與實作。
3. 選一個主分類。再加 0–3 個有檢索價值的主題標籤；沒有必要就不加。
4. 有既定連載才選系列；不為一次性文章預先開新主分類。

這個規則允許短文、純技巧和純開箱，不要求文章「足夠有深度」才適合放上網站。若某篇仍在兩類之間，問「讀者帶著哪個問題進來會最滿足」，不用讓所有提過的概念都成為分類。

| 待寫／既有例子 | 建議主分類 | 可選標籤或系列 |
| --- | --- | --- |
| Obsidian 如何整理文章並發布到網站 | 生活與實作 | Obsidian；不必先新建數位工具主分類 |
| 某間店家／飯店的體驗與開箱 | 生活與實作 | 場所名稱可直接留在標題、正文讓搜尋找到；不必每店一標籤 |

| 我如何用 Obsidian 理解自己的情緒 | 身體與自己 | Obsidian；若核心其實是操作步驟則改生活與實作 |
| 游泳換氣的練習紀錄 | 生活與實作 | 游泳 |
| 疤痕如何影響游泳與自己的身體感 | 身體與自己 | 游泳、病痛；不只看「游泳」字面 |
| 素描課系列 | 生活與實作 | 素描系列；個別文章可跨連正念 |

## 把分類、標籤與專題分工

主分類是主要入口，標籤是跨文章的查找線索，專題則是有人帶路的閱讀路線。它們不需要長成三套龐大的選單。

- 導覽以四個主分類、專題、搜尋／關於為主，不在每個地方展開 41 個標籤。
- 先維持目前 tags 技術結構，整理顯示方式與名稱字典；不急著新增多套 Hugo taxonomy。
- 專題先保留會所模式，規劃聆聽疼痛、正念的河流。每頁有簡介與「先讀這三篇」，不要只複製最新文章列表。
- 會所仍可在首頁有專區；它屬於助人工作且橫跨實習、手冊、日誌，不再與四個主分類共同計數。
- 書摘、閱讀心得、電影心得、講座筆記是形式或素材入口，可在閱讀頁篩選，無須成為全站主分類。
- 有順序的系列使用明確成員與順序資料。現有 `post_sequence_nav.html` 使用 `PrevInSection/NextInSection`，整理目錄時會影響上一篇／下一篇，並不等同真正的系列導航。

標籤整理採先定義、再映射：

| 現況 | 處理方向 |
| --- | --- |
| 電影 30、電影心得 32 | 語義接近，但集合不完全相同；先列例外再合併，保留舊標籤 URL |
| 聆聽疼痛 4、聆聽疼痛計畫 12 | 前者包含書籍相關內容，後者包含訪談計畫；可以同進一個專題，不能因名字相似直接當同一系列 |
| 正念的河流 21 | 跨閱讀、自我與日常，保留跨類串連，不強制搬到同一個資料夾 |
| 會所模式、會所實習、工作日誌、手冊 | 以專題＋系列顯示，降低選單重複感 |
| Shamless／無恥之徒 | 作品命名字典待修正；若改 tag，要連同舊入口保留 |
| 只用一次的作品／人名 | 不需要一律刪除；能用全文搜尋找到且無延伸閱讀價值時，可不再新增同類 tag |

未來新主題先用文章與搜尋存在；當確實有幾篇內容、可写清楚介紹並帶讀者繼續看，再升為可見專題。這比訂死「滿幾篇一定升級」更接近你的寫作方式。

## 改版與網址應如何分開處理

第一輪只改導覽、分類資料與 front matter，不搬既有文章。資料夾可暫時保留舊名字，即使畫面上的分類已更新；檔案整理是另一項工作，不必綁在分類改版上。

實作時要同步盤點 `hugo.yaml`、`data/taxonomy-landing.yaml`、`data/featured-tags.yaml`、`layouts/partials/site-nav-items.html`、`home-axis-data-clean.html` 與分類／標籤的 `_index.md`。目前導航直接写有分類名稱與網址，單改 front matter 會留下舊選單。建議把顯示名稱、排序、入口路徑集中為一份資料，桌機與手機共用；分類統計使用 blog＋clubhouse 的文章聯集，避免會所重複加總。

若日後需要整理文章目錄，先在每篇寫入 inventory 記錄的舊 `url`，再移動來源與同 bundle 圖片。只保留 `slug` 並不能保證跨 section 移動後 URL 不變。建立新文章時可考慮單層穩定路徑，但不把這個規則直接套用全站舊文章。

若真正要改網址：

1. 用舊 canonical → 新 canonical 的明確映射表作唯一紀錄，不能靠標題相似度猜測。
2. 先處理留言與互動識別：目前 comments 與 post_interactions_v2 都使用 `.RelPermalink`。301 只能帶人到新頁，不會自動合併舊的留言／閱讀量／按讚。須保留舊識別值或另外規劃資料遷移。
3. 將舊 canonical 及所有歷史 alias 直接指向最後目的地，避免層層串接；合併分類亦要處理舊分類頁、RSS 與分頁。
4. Hugo aliases 預設產生 HTML refresh，並非 HTTP 301。對外的重要舊網址可由映射表產生 Cloudflare `_redirects` 的精確 301；先確認目標存在、規則不重疊，再部署。[Hugo URL 說明](https://gohugo.io/content-management/urls/)
5. Cloudflare `_redirects` 有靜態／動態規則數與順序限制；不要拿一條廣泛規則猜所有歷史文章的去向。[Cloudflare 官方說明](https://developers.cloudflare.com/pages/configuration/redirects/)
6. 改後在全新目錄建置，跑 URL guard、搜尋與正文內連結檢查，再驗證部署的 HTTP 狀態、Location、canonical、sitemap、RSS、圖片、系列上下篇與留言識別。

不建議在這階段跑 `audit-aliases.ps1 -FixKnownNoise` 或舊的 taxonomy migration 腳本。前者有依文字特徵刪 alias 的行為，後者仍包含舊分類名称與舊遷移目的；既有歷史 URL 應先全部留下，再用證據判斷是否淘汰。

## 檢查结果與尚待補足

全新 Hugo 建置成功；URL guard 對自身基準檢查 0 個回歸；7 個守門工具測試通過。這不等於整站沒有既有問題。

離線規則檢查發現三個既有解析疑點：`/404.html` 被 `/:path.html` 規則導向沒有輸出的 `/404/`；兩個 `/blog/邁向助人工作`（有／無尾斜線）轉到本機沒有列表輸出的 `/blog/助人工作/`。這些保留為基準問題，需要在部署端實測；不宣稱已證實全都是真實 HTTP 404，也沒有在分類準備時擅自改掉。

正式站 sitemap 尚未成功取得，也尚未取得 Search Console 的已索引／404 網址匯出與 Cloudflare 帳戶層轉址。因此完整遷移前還要補正式來源清單，與本機基準取聯集。GitHub 舊網域、Vercel 舊網域的轉址也不在此 repository 的守門工具涵蓋範圍內。

下一步適合先用四類方案挑 15–20 篇跨界文章做人工試分，確認作者使用時不會一直猶豫，再改導覽與分類顯示。若試分後依然很想保留「病痛經驗」的獨立入口，就採五類備案，不需推倒這次做好的網址保護。
