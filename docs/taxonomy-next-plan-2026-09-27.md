- 昨天已完成第一人稱文案、分類介紹、人工導讀、統計說明與手機介紹顯示。本機歷史包含 PR #52 合併。

## 現存問題與證據

| 問題 | 目前看到什麼 | 對讀者的影響 |
| --- | --- | --- |
| 會所層級不一致 | 首頁六張同級卡；主選單放在助人工作底下；首頁另列會所區塊 | 容易以為會所與助人是兩個互斥分類 |
| 子入口像分類，其實是跨類標籤 | 日常卡放講座筆記、病痛卡放正念的河流；日常選單放詩的語言、助人選單放家族治療 | 點進去的內容可能不屬於剛選的分類 |
| 同名入口內容不同 | 助人工作、病痛經驗各有 category 與 tag；會所有 section 與 tag | 同一名稱出現不同篇數與列表 |
| 分類邊界待驗證 | 日常／自己、病痛／自己、閱讀／助人存在跨界文章 | 改名可能仍無法解決歸類困難 |

| 系列與搜尋待查 | 舊稽核記錄會所日誌查詢漏找；系列目前缺編號導覽 | 知道名稱仍可能找不齊，接續閱讀不方便 |

## 我的執行計畫

### 第一批：做出可判斷的入口方案

1. 重算各分類與 tag 的交集，列出目前每個卡片／選單項目的目的地、範圍與篇數。
2. 對日常的講座筆記、病痛的正念、日常的詩、助人的家族治療，逐項提出移除、替換或標成跨類延伸的建議。不為配合選單搬文章。
3. 做桌機與手機的入口預覽：以「五類＋獨立會所區塊」為建議版，對照現況；主選單先保留五類直達。
4. 交付入口對照表與預覽，讓作者決定會所呈現、選單方向。

### 第二批：檢驗分類名稱與內容邊界

1. 人工讀 15～20 篇跨界文章：日常／自己 5 篇、病痛／自己 5 篇、閱讀／助人 5 篇，另納入雙 category 的〈課堂報告小結〉及必要補充。
2. 每篇記錄主要問題、現分類、建議分類、可用 tag、理由及是否需作者判斷。
3. 用試分結果寫五類的簡短收錄準則，保留例外；日常不定義為零碎或剩餘，病痛詩不因形式就移到日常。
4. 只有出現具體理解問題才提改名；先區分顯示名稱與 URL。此時再決定是否需要改「閱讀與筆記」。

### 第三批：落實已選的入口與資料規則

1. 調整首頁、分類總覽及主選單，保留昨天的第一人稱文案並依回饋微調。
2. 統一分類 key、顯示名、順序與主要目的地的資料來源；長文介紹仍由內容頁管理。
3. 會所站內主要連結指向 section；同名 tag 舊入口先保留。需要合併或改 URL 時另建首頁、分頁、RSS mapping。
4. 分批處理 tag 合併；不將「聆聽疼痛」與「聆聽疼痛計畫」、或「成為一個人」與「成為自己」視為同義詞。

### 第四批：續讀與驗收

- 重現會所搜尋漏找，確認原因後修正；系列目錄依編號排列，不假定日期順序等於系列順序。
- 入口改動驗收桌機／手機、點擊目的地、篇數口徑與水平溢出。
- 執行 Hugo 建置、URL guard、既有 Playwright；涉及搜尋時補 Pagefind 與搜尋檢查。
- 如有網址變動，補 canonical、RSS、sitemap 與 redirect mapping 驗證。

## 工具與工作範圍

這項工作使用現有 Git、Node、Python，以及專案指定的 Hugo、Pagefind、Playwright 即可，不需要新增外部服務。工具準備以專案內可攜安裝為主，不修改全機 PATH。

本輪已安裝 Hugo extended 0.160.1（與 CI 一致）、可攜 npm 10.9.2，並依 lockfile 安裝專案依賴，含 Pagefind 1.5.2 與 Playwright。npm 安裝回報 0 vulnerabilities。工具放在 Git 忽略的 `.tmp/audit-tools/`，套件放在 `node_modules/`。

工具驗證發現一項前置問題：Hugo 可回報版本，但實際建置在此 Windows 環境發生 Go runtime `found pointer to free object`，結束碼 2，未產生完整網站。降低並行度後仍發生；原因尚未定位，不能宣稱網站建置通過。對不完整輸出執行的 URL guard 結果不作為網站回歸判定。下一輪做入口預覽前，先排除這個建置阻礙，再跑正式驗證。

第一階段已執行低風險入口修正：首頁版型、六張卡片、順序、文章分類與網址均保留；分類總覽的固定標籤區改稱「精選主題」，並移除日常書寫的零交集「講座筆記」與病痛經驗的零交集「正念的河流」卡片入口。這些標籤仍可在全站標籤區或其他文章脈絡找到。

Playwright Chromium、Headless Shell 與相關執行元件也已下載到 `.tmp/audit-tools/browsers/`。

可攜工具使用方式（PowerShell，專案根目錄）：

## 追加提案：先把「閱讀與筆記」顯示為「閱讀筆記」

9/27 作者提出先評估這項改名；目前是計畫，尚未視為正式實作決定。

### 建議範圍

先統一讀者看到的名稱為「閱讀筆記」，保留目前分類資料鍵 `閱讀與筆記`、分類網址 `/categories/閱讀與筆記/`、文章網址與文章歸屬。這樣可以先檢驗新名稱，不同時進行網址遷移。

「閱讀筆記」較精簡，但讀者可能以為只收書籍，因此分類介紹與卡片保留「讀書、看電影、聽講座」的範圍說明。書摘、閱讀心得、電影心得、講座筆記／心得仍依原本內容規則收錄，不因改名調整歸屬。

### 實作步驟

1. 建立共用的分類顯示名稱解析，優先取分類內容頁 title，找不到時退回原資料名稱。分類識別與集合查詢繼續使用原 key，避免把顯示名稱拿去查 taxonomy。
2. 將閱讀分類頁 title 改成「閱讀筆記」，同步首頁卡片、分類總覽、桌機／手機選單、分類側欄、文章分類連結與卡片標籤。硬編碼的顯示名稱改用同一解析邏輯。
3. 檢查搜尋索引／結果中的分類名稱、麵包屑、頁面 title、Open Graph 與結構化資料；顯示用名稱同步更新，canonical 與 RSS 連結保留原網址。
4. 不對整個專案做文字全域取代。原分類 key、網址、歷史文件、遷移腳本與 URL 基準中的舊名稱有各自用途，需區分保留。
5. 先解決本機 Hugo 建置阻礙，再做桌機／手機預覽與驗收；本輪改名與其他入口結構調整分開交付。

### 驗收標準

- 首頁、分類總覽、閱讀分類、代表文章、搜尋頁的讀者可見名稱一致。
- 建置前後閱讀分類文章成員完全相同，篇數相同，沒有意外新增第二個分類。
- 舊分類首頁、分頁、RSS 與文章連結繼續可用；URL guard 無新增回歸。
- 書摘／閱讀心得／電影心得等入口仍可正常使用，手機選單與卡片無溢出。
- 搜尋「閱讀筆記」能辨識該分類；另驗證舊稱是否仍可找到，必要時加入搜尋別名，不假定 Pagefind 會自動支援。

### 盤點結果與第二階段

原名稱分布在 `hugo.yaml`、卡片資料、導覽與卡片模板、分類內容頁，以及文章 front matter 等處。文字搜尋命中 91 個 blog／clubhouse 檔案；這是檔案命中數，不等同已發布文章數。

舊遷移腳本 `scripts/taxonomy_migration.py` 還將「閱讀筆記」映射回「閱讀與筆記」，後續若要改資料鍵必須重新檢視，不能直接重跑。

若日後確定網址也要改為 `/categories/閱讀筆記/`，再單獨做第二階段：分類資料鍵與名稱同步、舊首頁／各分頁／RSS 對應表、redirect、canonical、sitemap 與搜尋驗收。文章網址不因分類改名而搬移。本提案不需要第二階段才能上線。
